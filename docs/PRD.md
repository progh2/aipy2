## 1. 이 문서의 범위

학습 콘텐츠(레슨·예제·문제)는 이미 완성되어 운영 중입니다. 이 문서는 그 위에 얹을 **수업 운영 기능**만 다룹니다.
학생 계정과 명단, 학습 기록 동기화, 참여 현황 모니터링, 수업 중 화면 따라가기, 주제별 이해도 피드백,
과제 제출과 자동채점, 교사 관리 페이지가 대상입니다.

콘텐츠 자체의 추가·수정은 기존 방식(`tools/web/` 수정 후 재생성)을 그대로 따르며 이 문서의 범위가 아닙니다.

## 2. 배경과 해결할 문제

지금 사이트는 학습 기능은 충분하지만, **수업을 운영하는 데 필요한 정보가 교사에게 전혀 도달하지 않습니다.**

| 현재 상태 | 수업 중 실제로 생기는 문제 |
| --- | --- |
| 학습 기록이 브라우저 `localStorage`에만 있음 | 학생이 실습실 PC를 바꾸거나 초기화하면 기록이 사라짐. 집에서 이어서 못 함 |
| 교사가 진행 상황을 볼 수 없음 | 30명 중 누가 막혀 있는지 돌아다니며 확인해야 함. 조용히 못 따라오는 학생을 놓침 |
| 제출 개념이 없음 | 과제 확인이 화면 육안 확인이나 별도 채널로 흩어짐 |
| 수업 중 위치 안내가 말로만 이뤄짐 | "1단원 세 번째 주제 스크롤 내려서" — 매 전환마다 몇 명은 길을 잃음 |
| 어느 설명이 어려운지 알 방법이 없음 | 학생 반응을 표정으로만 추측. 다음 학기 콘텐츠 개선 근거가 남지 않음 |

## 3. 사용자와 시나리오

**학생** (2학년, 반당 25~30명, 학교 실습실 PC 또는 개인 노트북)

> 실습실 PC에 앉아 학교 계정으로 로그인한다. 지난 시간에 집에서 풀던 문제가 그대로 이어진다.
> 선생님이 새 주제를 설명하기 시작하면 내 화면이 그 주제로 부드럽게 이동한다.
> 설명이 잘 안 잡혀서 주제 아래 **어려워요**를 누른다. 코드를 고치다 막혀서 **도움 요청**을 누르고 계속 시도한다.
> 과제 문제를 통과시키고 제출한다.

**교사** (수업 진행 중, 교실 앞 화면 + 노트북)

> 관리 페이지에서 2학년 3반 수업 세션을 시작한다. 접속한 학생 28명이 보인다.
> 설명할 주제를 클릭하면 학생 화면이 따라온다. 실습 시간에는 학생 목록을 본다 —
> 3명이 도움 요청, 5명이 특정 주제에 **어려워요**를 표시했다. 그 주제를 한 번 더 짚는다.
> 수업 후 반별 진행률과 미제출자를 확인하고, 제출 소스 몇 개를 열어본다.

**교사** (학기 준비)

> 명단 CSV를 올려 학번·입학년도·학년·반을 등록한다. 학기 말에 기록을 CSV로 내보내고 학생 데이터를 정리한다.

## 4. 목표와 성공 기준

| 목표 | 성공 기준 |
| --- | --- |
| 학습 기록이 기기에 묶이지 않는다 | 학교 PC ↔ 개인 기기에서 같은 진행 상황이 보인다 |
| 교사가 반 전체 상황을 한 화면에서 본다 | 반 선택 후 3초 안에 학생별 진행·이해도·도움 요청이 보인다 |
| 수업 중 "지금 어디" 안내가 사라진다 | 교사가 주제를 클릭하면 따라가기를 켠 학생 화면이 5초 안에 이동한다 |
| 어려운 지점이 데이터로 남는다 | 학기 말에 주제별 이해도·정답률 하위 항목을 뽑아 콘텐츠를 보강한다 |
| 로그인 없이도 학습이 가능하다 | 네트워크·계정 장애 시 기존과 동일하게 동작한다 |

## 5. 범위에서 제외 (Non-goals)

- **공식 성적 산출 시스템이 아닙니다.** 자동채점은 형성평가와 실습 확인용이며, 공식 평가는 학교 절차를 따릅니다.
- **감시 도구가 아닙니다.** 화면 캡처·키 입력 기록·카메라·원격 제어·사이트 이탈 감지를 하지 않습니다.
  "따라가기"는 학습 문서의 위치를 옮기는 것뿐이며 학생 PC를 제어하지 않습니다.
- **정답 보안을 제공하지 않습니다.** 공개 정적 사이트이므로 정답은 열람 가능합니다.
- 학생 간 채팅·게시판은 만들지 않습니다. 질문은 도움 요청 신호와 대면 수업으로 처리합니다.
- 학부모 계정, 타 과목 확장, 시간표 연동은 이번 범위가 아닙니다.

## 6. 제약 조건

1. **정적 호스팅** — GitHub Pages입니다. 서버 비밀을 둘 수 없어 Admin SDK를 사용하지 않습니다.
   모든 권한 판단은 Firestore 규칙이 하며, 규칙 파일은 공개를 전제로 작성합니다.
2. **무료 플랜 기준** — Firestore Spark 플랜(하루 읽기 5만 / 쓰기 2만 / 삭제 2만, 저장 1GiB) 안에서 설계합니다.
   실시간 기능의 쓰기 빈도를 반드시 억제합니다(§11).
3. **학교망과 공용 PC** — CDN 접근이 필요하고, 여러 학생이 같은 PC를 씁니다. 로그아웃 시 로컬 기록 처리 정책이 필요합니다.
4. **브라우저 채점의 신뢰성** — 채점이 학생 브라우저(Pyodide)에서 돌아가므로 결과 위조가 원리상 가능합니다.
   제출물에 소스와 출력을 함께 보관하고, 교사 브라우저에서 재실행해 검증합니다(F8).
5. **수업 시간 손실 금지** — 로그인·동기화 실패가 학습을 막아서는 안 됩니다. 모든 기능은 실패 시 기존 동작으로 후퇴합니다.

## 7. 기능 요구사항

### F1. 계정과 명단 관리

**F1.1 학생 로그인 — 구현 완료**
학교 Google 계정(`@e-mirim.hs.kr`)으로 로그인합니다. 개인 계정은 즉시 로그아웃되고 안내가 표시됩니다.
학번·학년·반·번호는 교사가 등록한 명단에서만 가져오며, 학생이 스스로 바꿀 수 없습니다(규칙에서 강제).
학생 식별은 **학번과 이름을 함께** 표시하는 것을 기본으로 하고, 학년·반을 보조로 붙입니다(예: `20314 홍길동 · 2학년 3반`).
학번은 앞자리 0이 유실되지 않도록 문자열로 저장합니다. 출석번호는 학번에 포함되어 있으면 생략할 수 있고, 없으면 학번순으로 정렬합니다.

**고유 식별자는 학교 이메일입니다.** 학번은 입학년도가 다른 학생끼리 겹칠 수 있으므로 단독으로 학생을 특정하지 못합니다.
따라서 명단은 `admissionYear`(입학년도)를 필수로 포함하고, 학생을 가리키는 조합은 항상 `admissionYear` + `studentId`입니다.
`grade`(현재 학년)는 학년도마다 바뀌지만 입학년도는 바뀌지 않으므로, 학년도 전환·졸업 처리와 이력 보존의 기준이 됩니다.

**F1.2 명단 일괄 등록 — 구현 완료** (`web/teacher/admin.html`)
교사가 CSV를 업로드해 `roster`를 채웁니다. 형식은 `email,studentId,admissionYear,name,grade,classroom,number`이며 `number`만 선택입니다.
**수업 전 학기 초 일괄 등록이 기본 흐름**이고, 학기 중 전학·누락은 개별 추가로 즉시 반영합니다.

- 업로드 전 미리보기: 신규 / 변경 / 중복 / 형식 오류를 건수와 함께 표시하고 교사가 확인 후 반영
- 쓰기는 배치로 처리하되 배치당 500건 제한을 고려해 분할
- 학교 도메인이 아닌 이메일, 필수 항목 누락, **같은 입학년도 안에서의 학번 중복**은 반영하지 않고 이유를 표시
  (입학년도가 다른 학번 중복은 정상이므로 경고하지 않습니다)
- 명단 편집(개별 수정·삭제)과 CSV 내보내기
- **개별 추가** — 수업 중에도 한 줄 입력으로 등록. 학생이 다시 로그인하면 즉시 반영되고, 이미 로그인한 학생은 새로고침으로 반영

**F1.3 미등록 로그인 처리**
명단에 없는 학교 계정도 로그인은 됩니다(수업을 막지 않기 위해). 학번·학년·반이 비어 있고 학생에게 안내가 표시됩니다.
교사 페이지에 **미배정 학생** 목록이 뜨고, 클릭 한 번으로 학번·학년·반을 배정합니다.

**F1.4 입학년도와 학년도 관리**
`admissionYear`로 학생 코호트를 구분합니다. 학년 진급 시 `grade`와 `classroom`만 갱신하고 입학년도는 그대로 두므로,
이전 학년의 학습 기록이 같은 학생에게 계속 이어집니다. 졸업생은 입학년도 기준으로 일괄 조회·보존·정리합니다.

**F1.5 교사 권한**
`admins/{학교이메일}` 문서로 부여하며 콘솔에서만 관리합니다. 클라이언트에서 권한을 만들 수 없습니다.

### F2. 학습 기록 동기화

지금의 `localStorage` 상태 객체(`complete` 완료 체크 / `answers` 문제 답안 / `journals` 저널 / `projects` 편집 중 코드)를
`students/{uid}/state/current`에 그대로 미러링합니다. 스키마를 그대로 옮기므로 **문제나 주제를 추가해도 동기화 코드를 고칠 필요가 없습니다.**

- **로컬 우선** — 화면은 항상 로컬 상태로 즉시 반응하고, 클라우드 동기화는 뒤에서 진행합니다
- **쓰기 억제** — 타이핑마다 쓰지 않습니다. 유의미한 사건(완료 체크, 문제 정답, 제출)에서 즉시,
  코드 편집은 약 20~30초 유휴 시점과 페이지 이탈 시에만 씁니다
- **충돌 처리** — 문서 단위 최종 쓰기 승리는 기록을 잃을 수 있으므로 **항목 단위 병합**을 씁니다.
  같은 항목이 양쪽에 있으면 항목별 갱신 시각이 늦은 쪽을 채택하고, 코드(`projects`)만 충돌 시 학생에게 선택을 요청합니다
- **폴백** — 로그인 안 함·네트워크 실패·규칙 거부 시 조용히 로컬만 사용하고, 상태만 헤더에 표시합니다
- **공용 PC** — 로그아웃 시 이 브라우저의 로컬 기록을 지울지 묻습니다. 클라우드 기록은 유지됩니다

**요약 문서** `progress/{uid}`를 함께 갱신합니다. 교사 페이지는 이 요약만 읽으므로 학생 30명 현황을 30회 읽기로 표시할 수 있습니다.
요약에는 단원별 완료 수, 문제 시도·정답 수, 주제별 이해도(F5), 마지막 활동 시각이 들어갑니다.

### F3. 참여 현황 모니터링 (교사 관리 페이지)

**F3.1 반 현황 보드**
교사는 화면 상단에서 **지금 수업하는 반을 선택**하고, 선택된 반은 모든 화면에 항상 표시됩니다.
반이 모든 조회·집계·세션의 기준 단위이며, 여러 반이 동시에 수업 중이어도 서로 섞이지 않습니다.
반을 선택하면 학생 카드 목록이 나옵니다. 각 카드에 학번·이름, 접속 상태, 현재 보고 있는 주제,
단원별 완료율, 문제 정답률, 도움 요청, 이해도 신호, 마지막 활동 시각을 표시합니다.
정렬 기준: 도움 요청 → 진행 지연 → 번호순. **막힌 학생이 위로 올라오는 것이 이 화면의 핵심입니다.**

**F3.2 주제 × 학생 히트맵**
가로축 주제, 세로축 학생의 격자에서 완료·미완료·이해도를 색으로 표시합니다. 반 전체가 한 화면에 들어오게 합니다.
열(주제)을 클릭하면 그 주제에 막힌 학생만 필터링합니다.

**F3.3 문항 분석**
문제별 시도 수·정답률·평균 시도 횟수를 보여 줍니다. 정답률 하위 문항은 수업 중 다시 설명할 대상이자 문항 개선 대상입니다.

**F3.4 접속 상태(프레즌스)**
"지금 이 학생이 사이트를 열어 두고 있는가, 그리고 어느 단원·주제를 보고 있는가"를 교사 화면에 표시하는 기능입니다.
학생 브라우저가 짧은 신호를 주기적으로 보내고, 일정 시간 신호가 끊기면 이탈로 간주합니다.
교사 입장에서는 로그인 여부(계정)와 다릅니다 — 로그인은 했지만 창을 닫아 둔 학생을 구별하기 위한 것입니다.
쓰기 비용 때문에 실시간 초 단위가 아니라 **60~90초 주기 갱신**으로 하고, 화면에는 "1분 이내"처럼 근사값으로 표기합니다.
브라우저 탭이 숨겨지면 갱신을 멈춥니다.

**F3.5 개별 학생 상세**
한 학생의 진행·답안·제출물·저널·이해도 이력을 한 화면에서 봅니다. 상담과 개별 지원용입니다.

**F3.6 내보내기**
반별 진행·정답률·제출 현황을 CSV로 내보냅니다. 평가 기록 정리에 사용합니다.

### F4. 수업 따라가기 (Follow Mode)

교사가 설명할 부분을 클릭하면 학생 화면이 그 위치로 이동하는 기능입니다.

**F4.1 수업 세션 — 반 단위**
세션은 **반 하나에 하나**입니다. 교사가 수업할 반을 선택해 세션을 시작하며, 서로 다른 반의 세션은 동시에 존재할 수 있습니다.
학생은 자기 반의 세션만 구독하므로 옆 반 수업의 화면 이동에 끌려가지 않습니다. 세션 문서에 현재 **초점**(페이지, 주제 앵커, 선택된 예제)이 들어 있고,
학생 브라우저는 자기 반의 활성 세션을 실시간 구독합니다.

**F4.2 초점 이동**
교사 화면의 주제 목록이나 학생용 페이지에서 항목을 클릭하면 초점이 갱신되고, 따라가기를 켠 학생 화면이 이동합니다.

- 같은 페이지 안의 주제 이동: 부드러운 스크롤로 즉시 이동
- 다른 단원 페이지로 이동: 로컬 상태를 저장한 뒤 이동. **편집 중인 코드는 절대 잃지 않습니다**
- 예제 선택까지 함께 전달할 수 있습니다(실습실 편집기가 같은 예제를 열도록)

**F4.3 학생의 자율성 — 설계 원칙**
강제 이동은 학생이 하던 작업을 끊고 멀미를 유발합니다. 기본 동작은 다음과 같습니다.

- 따라가기는 **기본 켜짐**(확정)이며 학생이 언제든 끌 수 있습니다
- 학생이 스스로 스크롤하면 따라가기가 자동으로 **일시 해제**되고,
  상단에 `선생님 화면으로 돌아가기` 버튼이 남습니다. 실습 중 자기 코드를 보다가 화면이 튀는 일이 없습니다
- 교사는 **시선 모으기**(잠깐 주목) 신호를 따로 보낼 수 있습니다. 화면 상단 배너로 표시하며 이동은 하지 않습니다
- 화면 잠금 모드는 만들지 않습니다(§5 Non-goals)

**F4.4 교사 피드백**
교사 화면에 "따라오는 중 24명 / 따로 보는 중 4명"을 표시합니다. 숫자만 보여 주고 개인 지적용으로 쓰지 않습니다.

**F4.5 세션 종료**
교사가 종료하거나 일정 시간(예: 2시간) 후 자동 만료합니다. 세션이 없으면 따라가기 UI는 나타나지 않습니다.

### F5. 주제별 이해도 신호와 내용 피드백

각 학습 주제 끝에 **이해했어요 / 조금 어려워요 / 어려워요** 버튼을 둡니다. 지금의 완료 체크박스 옆에 나란히 놓습니다.

- 한 번 누르면 저장되고 언제든 바꿀 수 있습니다. 누르지 않아도 학습에는 영향이 없습니다
- **어려워요**를 누르면 "어디가 막혔나요?"라는 선택 입력(한 줄, 200자 이내)이 열립니다. 비워도 됩니다
- 학생 화면에도 자기 이력이 남아, 복습할 주제를 스스로 고를 수 있습니다
- 값은 `progress/{uid}`의 이해도 맵에 담기므로 교사가 반 전체를 적은 읽기로 집계할 수 있습니다.
  텍스트 코멘트는 분량과 민감도가 다르므로 별도 컬렉션에 저장합니다

**교사 쪽 활용**

- 실시간: 수업 중 방금 설명한 주제에 **어려워요**가 몇 명인지 보고 즉시 다시 짚습니다
- 누적: 주제별 이해도 분포를 정렬해 **어려운 주제 순위**를 봅니다.
  정답률(F3.3)과 겹쳐 보면 "설명이 어려운 주제"와 "문제가 어려운 주제"를 구분할 수 있습니다
- 콘텐츠 개선 루프: 어려워요가 몰린 주제는 `tools/web/content.py`의 설명·예제를 보강할 근거가 됩니다.
  **이 저장소는 콘텐츠를 코드로 관리하므로, 피드백이 바로 다음 학기 교재 개선으로 이어집니다**

**공개 범위(확정)** — 교사에게 **학번과 이름을 함께** 표시합니다. 개별 지원이 목적이기 때문입니다.
대신 "어려워요는 도움 요청 신호이며 평가에 반영되지 않는다"를 해당 UI에 직접 적어 솔직한 응답이 모이게 합니다(§12).

### F6. 도움 요청

학생이 막혔을 때 손을 들지 않고도 신호를 보낼 수 있게 합니다.

- 실습실과 문제 영역에 **도움 요청** 버튼. 현재 주제·예제·마지막 오류 메시지가 함께 담깁니다
- 교사 화면 상단에 대기 큐로 표시(요청 시각순). 교사가 처리하면 해결 표시
- 학생은 요청을 취소할 수 있고, 요청 후에도 계속 시도할 수 있습니다
- 오류 메시지를 함께 보내면 교사가 가기 전에 원인을 짐작할 수 있어 대응이 빨라집니다

### F7. 과제와 제출

**F7.1 과제 정의 — 코드 수정 없이**
과제를 Firestore에 데이터로 만듭니다. 교사가 관리 페이지에서 **기존 문제·예제를 골라** 과제를 구성합니다.

```
assignments/{과제id}
  title, description, targets: [{type:'question'|'example', id}], classrooms: [], openAt, dueAt, open
```

기존 문제 213개와 예제 82개가 모두 과제 대상이 되며, **문항마다 별도 개발이 필요하지 않습니다.**
콘텐츠가 늘어나면 과제 대상도 자동으로 늘어납니다.

**F7.2 제출**
학생이 검사를 통과한 뒤 제출을 누르면 다음이 저장됩니다.

```
students/{uid}/submissions/{과제id}
  targets별: 소스 파일 전체, 실행 인자·표준 입력, 채점 결과, 실행 출력(길이 제한), 시도 횟수, 제출 시각
```

- 통과하지 않아도 제출할 수 있습니다(확정). 막힌 상태 자체가 교사에게 필요한 정보이므로 상태를 `미통과 제출`로 구분해 남깁니다
- 마감 이후 제출은 `지연`으로 표시하되 막지 않습니다. 처리 방침은 교사가 결정합니다
- 제출 후 수정·재제출이 가능하며 이력을 남깁니다

**F7.3 교사 확인**
제출물 목록에서 소스와 출력을 열어보고 확인 표시나 한 줄 코멘트를 남깁니다. 학생은 자기 제출물에서 이를 확인합니다.

### F8. 유연한 자동채점과 재검증

**F8.1 기존 채점 구조를 그대로 사용**
현재 채점은 이미 데이터 주도입니다. 구현형 문제는 `checks`의 Python `assert`로 반환값·여러 입력·경계 조건을 검사하고,
빈칸은 정규화 후 대표 답안과 비교하며, 서술형은 자기 점검입니다. **채점 방식을 새로 만들지 않고 이 구조를 그대로 씁니다.**

**F8.2 채점 결과의 신뢰 수준을 명시**
채점은 학생 브라우저에서 실행되므로 위조가 가능합니다. 제출물에는 결과와 함께 **소스와 출력을 항상 보관**하고,
화면에 "브라우저 채점 결과"임을 표시합니다. 신뢰가 필요한 평가에는 F8.3을 사용합니다.

**F8.3 교사 브라우저 재검증**
교사 관리 페이지에서 제출 소스를 **교사 브라우저의 Pyodide로 다시 실행**해 검사를 재수행합니다.
서버 없이 신뢰성을 회복하는 방법이며, 한 반 분량을 순차 실행해 결과가 다른 제출을 표시합니다.

**F8.4 서술형 보조**
서술형은 자동채점하지 않습니다. 교사 화면에서 반 전체 답안을 나란히 읽고 확인 표시만 남깁니다.

### F9. 형성평가와 수업 리포트

**F9.1 함께 풀기 모드**
교사가 문제 하나를 세션 초점으로 지정하고, 반 전체의 선택형 응답 분포를 막대로 봅니다(개인 이름 없이).
오답이 몰린 선택지를 바로 다루는 것이 목적입니다.

**F9.2 수업 종료 리포트**
한 교시가 끝나면 자동 요약을 만듭니다: 진행한 주제, 완료율 변화, 어려워요 상위 3개, 미해결 도움 요청, 미제출자.
다음 차시 도입에 그대로 사용합니다.

### F10. 개인정보 운영 도구

- 수집 항목을 최소로 유지합니다: 학교 이메일, 이름, 학번·입학년도, 학년·반·번호, 학습 기록, 제출물, 이해도 신호
- 학생 화면에 **무엇이 저장되고 교사가 무엇을 보는지** 명확히 표시합니다
- 보관 단위는 입학년도(코호트)입니다. 교사가 **입학년도 기준으로 데이터를 일괄 조회·정리**할 수 있게 합니다
- 학생 본인의 기록 내보내기(JSON)는 기존 기능을 유지합니다
- 실제 운영 시 수집·보관·동의 절차는 학교 규정과 담당 부서 확인을 따릅니다

## 8. 데이터 모델

```
admins/{교사이메일}                    교사 권한. 콘솔에서만 관리
roster/{학생이메일}                    명단: studentId(문자열), admissionYear, name, grade, classroom, number(선택)
students/{uid}                         프로필: email, studentId, admissionYear, name, grade, classroom, number
students/{uid}/state/current           학습 기록 미러 (complete, answers, journals, projects)
students/{uid}/submissions/{과제id}     제출: 소스, 입력, 채점 결과, 출력, 시도, 제출 시각
progress/{uid}                         요약: 단원별 완료 수, 문제 시도·정답, 이해도 맵, 마지막 활동
presence/{uid}                         접속 상태: 현재 페이지·주제, 갱신 시각, 따라가기 여부
sessions/{반}                          수업 세션(반 단위, 반당 하나): 교사, 활성 여부, 초점(페이지·주제·예제), 주목 신호
helpRequests/{요청id}                   도움 요청: 학생, 반, 주제, 오류 요약, 상태, 시각
feedback/{피드백id}                     이해도 코멘트 텍스트 (분량·민감도 때문에 요약과 분리)
assignments/{과제id}                    과제 정의: 대상 문제·예제, 반, 기간, 공개 여부
```

**설계 의도**

- **문서 ID는 이메일 또는 계정 uid입니다.** 학번을 키로 쓰지 않으므로 입학년도가 바뀌어도 문서가 충돌하지 않습니다
- 교사 화면의 기본 조회는 `progress`와 `presence`만 봅니다. 학생 원본을 전부 읽지 않아 반 규모가 커져도 빠릅니다
- 학습 기록은 기존 `localStorage` 스키마를 그대로 옮깁니다. 콘텐츠가 늘어도 동기화 코드를 고치지 않습니다
- 과제는 코드가 아니라 데이터입니다. 문항 추가 때 개발이 필요 없습니다

## 9. 권한 모델

| 데이터 | 학생 | 교사 |
| --- | --- | --- |
| `roster` | 자기 한 줄만 읽기 | 전체 읽기·쓰기 |
| `admins` | 자기 문서만 읽기 | 콘솔에서만 변경 |
| `students`, `state`, `submissions` | 자기 것만 읽기·쓰기 | 읽기 (삭제는 교사만) |
| `progress`, `presence` | 자기 것만 쓰기 | 전체 읽기 |
| `sessions` | 읽기, 따라가기 상태만 쓰기 | 생성·수정 |
| `helpRequests` | 자기 요청 생성·취소 | 읽기·상태 변경 |
| `assignments` | 공개된 과제 읽기 | 생성·수정 |

전제는 세 가지입니다. **학교 도메인 + 이메일 인증 확인**, **학생은 자기 반·번호를 명단 값으로만 쓸 수 있음**,
**교사 권한은 클라이언트에서 생성 불가**. 현재 규칙에 이미 반영되어 있고 새 컬렉션에도 같은 원칙을 적용합니다.

## 10. 실패 시 동작

| 상황 | 동작 |
| --- | --- |
| 설정값 미입력 | 로그인 UI를 표시하지 않고 기존 사이트로 동작 |
| 네트워크 단절 | 로컬 학습 계속. 헤더에 동기화 대기 표시, 복구 시 자동 반영 |
| 규칙 거부 | 학습을 막지 않고 안내만 표시. 콘솔에 원인 기록 |
| 명단 미등록 | 로그인 허용, 반·번호 없음, 교사 화면의 미배정 목록에 노출 |
| 세션 없음 | 따라가기 UI 미표시 |
| 할당량 초과 | 동기화 주기를 늘리고 학습은 계속. 교사에게 경고 표시 |

## 11. 비용과 할당량

Spark 플랜 기준 하루 읽기 5만 / 쓰기 2만입니다. 반 30명, 하루 6교시를 가정한 개산입니다.

| 항목 | 추정 |
| --- | --- |
| 접속 상태 갱신 (90초 주기, 50분) | 약 33회 × 30명 ≈ 1,000 쓰기 / 교시 |
| 학습 기록 동기화 (유의미한 사건 + 유휴 저장) | 학생당 20~40회 ≈ 600~1,200 쓰기 / 교시 |
| 세션 초점 구독 | 초점 변경 1회당 학생 수만큼 읽기. 40회 변경 ≈ 1,200 읽기 / 교시 |
| 교사 보드 (progress 구독) | 초기 30 읽기 + 변경분만 |

교시당 쓰기 약 2,000건이면 6교시에 12,000건으로 한도 안입니다. 다만 **여러 반이 동시에 수업하면 한도에 근접**하므로
다음을 지킵니다.

- 접속 상태 갱신 주기는 설정값으로 두고 기본 90초. 탭이 숨겨지면 중단
- 학습 기록은 타이핑마다 쓰지 않음(§F2)
- 규칙 안의 `get()`/`exists()`도 읽기로 과금되므로 계정 확인을 먼저 실패시키는 현재 순서를 유지
- 한도 초과 시 Spark는 청구 없이 중단됩니다. Blaze로 올릴 경우 예산 알림을 필수로 설정
- 프레즌스 쓰기가 병목이 되면 해당 기능만 Realtime Database(동시 접속 100, 전송량 과금)로 옮기는 것을 검토

## 12. 신뢰와 윤리

이 기능들은 학생을 감시하는 것이 아니라 **막힌 학생을 빨리 찾기 위한** 것입니다. 그 전제가 학생에게 전달되어야 데이터가 정직해집니다.

- 학생 화면에 무엇이 기록되고 교사가 무엇을 보는지 명시합니다
- **어려워요와 도움 요청은 평가에 반영되지 않습니다.** 이 문구를 해당 UI에 직접 적습니다
- 따라가기는 학생이 끌 수 있고, 화면 잠금은 제공하지 않습니다
- 교사 화면의 따라가기 통계는 인원수만 표시하고 개인 지적에 쓰지 않습니다
- 채점 결과는 "브라우저 채점"임을 표시하고, 신뢰가 필요한 경우 재검증 결과를 사용합니다

## 13. 로드맵 개요

각 단계는 그 자체로 수업에 쓸 수 있는 상태로 끝냅니다. 상세 이슈 분해는 별도로 작성합니다.

| 단계 | 내용 | 선행 |
| --- | --- | --- |
| **M0. 학생 로그인** (완료) | 학교 계정 로그인, 명단 연동, 권한 규칙, 콘솔 설정 문서 | — |
| **M1. 명단과 교사 페이지 골격** | ~~CSV 일괄 등록·미리보기, 미배정 목록, 교사 권한 확인~~(완료), ~~반 선택 UI, 관리 페이지 레이아웃 확장~~(완료) | M0 |
| **M2. 학습 기록 동기화** | state 미러링, 항목 단위 병합, 요약 문서 갱신, 공용 PC 로그아웃 정책 | M0 |
| **M3. 이해도 신호와 도움 요청** | 주제별 이해했어요/어려워요, 코멘트, 도움 요청 큐, 교사 실시간 표시 | M2 |
| **M4. 참여 현황 보드** | 반 현황, 주제×학생 히트맵, 문항 분석, 학생 상세, CSV 내보내기 | M2, M3 |
| **M5. 수업 따라가기** (완료) | 세션 시작·종료, 초점 이동, 학생 자율 해제, 주목 신호, 프레즌스 | M1 |
| **M6. 과제와 제출** | 과제 정의 화면, 제출·재제출, 교사 확인·코멘트 | M2 |
| **M7. 재검증과 리포트** | 교사 브라우저 재실행 검증, 함께 풀기 모드, 수업 종료 리포트 | M6 |
| **M8. 운영 도구** | 학년 진급·입학년도 기준 정리, 졸업생 데이터 처리, 개인정보 안내 정비 | M1 |

**M5(따라가기)는 M2·M3에 의존하지 않으므로 M1 직후로 앞당길 수 있습니다.**
수업에서 가장 먼저 체감되는 기능이 무엇인지에 따라 순서를 조정하세요.
